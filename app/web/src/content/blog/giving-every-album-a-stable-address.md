_Part 5. Separating the music's identity from its location, April 2026._

Correcting an artist name should change what appears on screen. In early Crate, it could also change
where we expected to find the music. Artist names became directories, album names became paths, and
those paths travelled into playlists and playback requests.

That worked while the names stayed put. Enrichment, imports and repair jobs all had reasons to change
them. A provider could spell an artist differently, an album could gain a year directory, or a leading
dot could make an imported folder disappear from ordinary browsing. Every naming fix had the
potential to become a storage operation.

A track saved in a playlist had to remain playable after we corrected the album's name or moved its
files. Importing another copy of that album also needed to find the catalogue entry we already had.
That required both an address that stayed put and an identity an import could recognise.

Storage V2 first gave the existing rows addresses that would survive a rename. The later catalogue
identity work dealt with recognising the album when it arrived again. The order mattered: before
moving a file, we had to preserve the references that still knew it by its old path. That was the
part the [previous chapter's import workers](/blog/when-retries-repeat-a-download) could not solve by
coordinating their filesystem work alone.

## Attach the playlist before moving the album

A readable library such as `Artist/Year/Album/01 - Title.flac` carries useful information. You can
browse it over SSH, copy an album without opening an application, and often recover its meaning even
when its tags are incomplete. Crate began around that kind of collection.

The trouble was how far the path escaped. The catalogue stored it to locate audio, which was necessary.
Playlist entries also kept `track_path`; history and radio had path-based fallbacks. An import had to
work out which spelling of an artist's directory was already in use. Fixing a name therefore required
more than updating the artist row.

Our storage design listed these failures together: hidden folders, provider naming differences,
Unicode and punctuation, and references that depended on paths. We chose managed storage with opaque
identifiers for the artist, album and track. Display names would remain in the database and tags.
[Storage V2 design](https://github.com/thecrateapp/crate/blob/647a1d6164abf37cce5b2c8debea9547f32d8778/docs/plans/2026-04-13-library-storage-id-migration.md#L3-L43).

Keeping readable folders was a viable approach. Beets, for example, lets a library owner define paths
from metadata fields and provides disambiguation functions for similar albums. Its documentation also
explains why `$albumartist` is usually a better directory key than the artist credited on each track.
That is useful when the directory tree is part of how someone manages their collection.
[Beets path formats](https://docs.beets.io/en/stable/reference/pathformat.html).

Crate was increasingly managing the collection through an API, workers and Listen. We wanted a title
correction to leave the file address alone. Continuing to improve filename sanitisation would have
helped imports, but it would have left names in charge of storage identity.

We kept numeric database IDs for joins and added a `storage_id` UUID to each artist, album and track.
The initial choice was UUIDv4, generated by Python's standard library. The design explicitly considered
UUIDv7 and ULID, then rejected the extra format or implementation work for this use: the filesystem did
not need identifiers sorted by creation time.
[Identifier decision](https://github.com/thecrateapp/crate/blob/647a1d6164abf37cce5b2c8debea9547f32d8778/docs/plans/2026-04-13-library-storage-id-migration.md#L34-L56).

UUIDv4 supplies a random identifier; it does not encode the artist's name or recognise an existing
album. That distinction becomes useful later in the migration. [RFC 9562, UUIDv4](https://www.rfc-editor.org/rfc/rfc9562.html#section-5.4).

The album could now have a storage UUID while all its files remained in their readable directories.
The playlist still needed a link to the track row. A UUID on that row would not help an entry that
remembered only the old path.

The schema migration added `playlist_tracks.track_id`, backfilled the storage UUIDs, and matched old
playlist paths to catalogue tracks. Exact paths took priority; relative paths could match the end of
a catalogue path. Unmatched entries retained their compatibility data. This was a migration of existing
references, not a guarantee that an ambiguous path could identify the right recording.
[Schema and playlist backfill](https://github.com/thecrateapp/crate/blob/647a1d6164abf37cce5b2c8debea9547f32d8778/app/crate/db/core.py#L1747-L1797).

The UUID backfill changed only rows that did not yet have an identifier:

```python source="app/crate/db/core.py#L1763-L1773" commit="647a1d6164abf37cce5b2c8debea9547f32d8778" "uuid.uuid4()"
    for table, pk in (
        ("library_artists", "name"),
        ("library_albums", "id"),
        ("library_tracks", "id"),
    ):
        cur.execute(f"SELECT {pk} AS pk FROM {table} WHERE storage_id IS NULL")
        for row in cur.fetchall():
            cur.execute(
                f"UPDATE {table} SET storage_id = %s WHERE {pk} = %s",
                (str(uuid.uuid4()), row["pk"]),
            )
```

Unique indexes and `NOT NULL` constraints followed the backfill. Playlist reads then preferred the
track's numeric ID, with the old path branches kept for entries that had not been resolved. The
migration could update the path on the existing track row while an ID-based reference still pointed
to that row. [Playlist lookup](https://github.com/thecrateapp/crate/blob/647a1d6164abf37cce5b2c8debea9547f32d8778/app/crate/db/playlists.py#L25-L44).

At this point the file had not moved. The playlist could reach the track through `track_id`, and the
track still had the old path. We could change that path without replacing the row the playlist used.
Moving the files first would have removed the strongest match for entries that still held only a path.

## Move the file and update the same row

The physical layout became `/music/<artist-id>/<album-id>/<track-id>.<extension>`. Track order stayed
in metadata. We kept the extension because the file still had a format, but its title no longer
participated in the address. One helper built that path:

```python source="app/crate/storage_layout.py#L15-L23" commit="647a1d6164abf37cce5b2c8debea9547f32d8778"
def track_path(
    library_root: str | Path,
    artist_storage_id: str,
    album_storage_id: str,
    track_storage_id: str,
    extension: str,
) -> Path:
    suffix = extension if extension.startswith(".") else f".{extension}"
    return album_dir(library_root, artist_storage_id, album_storage_id) / f"{track_storage_id}{suffix.lower()}"
```

[Open the identity and migration diagram at full size](/blog/giving-every-album-a-stable-address/storage-identities.svg).

This made the directory tree less useful to a person inspecting it by hand. The database and tags had
to carry the readable information. We also needed to keep accepting raw music through staging rather
than expect people to invent managed paths themselves. That was part of the storage decision, not an
incidental cost of choosing UUIDs.

The album was ready to move. A worker ran the migration, with `/music` mounted writable. It could
target one artist or walk the collection. Within an artist it processed albums, emitted progress and
checked for cancellation.
It also used the processing marker from the import workflow to ask the watcher to leave that artist
alone while files moved.

For each track, the worker constructed the destination from the stored UUIDs, renamed the file and
updated the path on the same database row. The normal case used `os.rename()` on the same filesystem.
Python documents that successful rename as atomic on POSIX. It does not include the later database
update in that atomic operation. [Python rename semantics](https://docs.python.org/3.13/library/os.html#os.rename).

A process could therefore stop after moving the file but before saving its new path. The next attempt
needed to recognise that state. If the old file was missing, the worker checked the expected destination
and repaired the row when it found the file there:

```python source="app/crate/worker_handlers/migration.py#L96-L107" commit="647a1d6164abf37cce5b2c8debea9547f32d8778" "new_candidate"
        if not old_track_path.is_file():
            # Track file might already have been moved or doesn't exist
            new_candidate = target_album_dir / f"{track_storage_id}{old_track_path.suffix.lower()}"
            if new_candidate.is_file():
                # Already moved — just update DB
                with get_db_ctx() as cur:
                    cur.execute(
                        "UPDATE library_tracks SET path = %s, filename = %s WHERE id = %s",
                        (str(new_candidate), new_candidate.name, track_id),
                    )
                tracks_moved += 1
                continue
```

When the old file still existed, the worker attempted a rename and fell back to `shutil.move()` after
an `OSError`. That fallback allowed a copy-and-remove path across filesystems; it did not provide the
same atomicity as a successful rename. After moving tracks, the worker also handled album artwork and
updated the album directory. [Move and update sequence](https://github.com/thecrateapp/crate/blob/647a1d6164abf37cce5b2c8debea9547f32d8778/app/crate/worker_handlers/migration.py#L112-L153).

Inside the album worker, an album still recorded at its old readable path could reach these branches:

| State on the next attempt | What the first worker implementation did |
| --- | --- |
| Old album directory exists; the track is still at its old path | Attempt the move, then update the track row. |
| Old album directory exists; the old track path is missing but the UUID destination exists | Update the row to point at the destination. |
| Old album directory exists; neither track path contains the file | Increment `tracks_failed` and continue with other tracks. |
| Old album directory is gone | Return `source_missing` before reaching per-track recovery. |

[Album preconditions and per-track recovery](https://github.com/thecrateapp/crate/blob/647a1d6164abf37cce5b2c8debea9547f32d8778/app/crate/worker_handlers/migration.py#L66-L110).

There was another way to leave work behind. The album could return `migrated` with a nonzero
`tracks_failed` count, and its directory path was updated after the loop. A later run could recognise
that UUID-shaped path and skip the album. The artist shortcut also inspected only a sample of album
paths. A `migrated` result therefore needed checking even when the worker had finished normally.

The separate verification task checked both directions: catalogue tracks whose files were missing,
and audio files whose paths were absent from the catalogue. It was a path and existence check, with a
bounded orphan report. It did not compare audio hashes or prove that every copied file was intact.
[Migration checks and verification](https://github.com/thecrateapp/crate/blob/647a1d6164abf37cce5b2c8debea9547f32d8778/app/crate/worker_handlers/migration.py#L24-L53),
[verification implementation](https://github.com/thecrateapp/crate/blob/647a1d6164abf37cce5b2c8debea9547f32d8778/app/crate/worker_handlers/migration.py#L421-L483).

### The neighbouring album can keep its old directory

Moving this album did not mean the rest of the collection had moved. Migration could stop between
artists, and an installation could still contain unmanaged folders. Artwork and enrichment needed to
find both without guessing which storage generation an artist used.

We added `resolve_artist_dir()` and `resolve_album_dir()` instead of asking artwork, enrichment and
import code to reconstruct paths independently. The artist resolver considered the saved folder,
the UUID directory and the readable name. When the caller asked for an existing directory, it returned
the first candidate that was present. The album resolver preferred its stored path.
[Initial directory resolution](https://github.com/thecrateapp/crate/blob/647a1d6164abf37cce5b2c8debea9547f32d8778/app/crate/storage_layout.py#L41-L96).

The importer followed the same distinction. A managed artist received managed album and track names;
a legacy artist could continue using its existing readable layout. Sync learned to recognise UUID
components and recover metadata from tags and existing catalogue rows. A directory's opaque name
could no longer be assumed to be the artist's display name.
[Import destinations](https://github.com/thecrateapp/crate/blob/647a1d6164abf37cce5b2c8debea9547f32d8778/app/crate/storage_import.py#L91-L119),
[sync integration](https://github.com/thecrateapp/crate/blob/647a1d6164abf37cce5b2c8debea9547f32d8778/app/crate/library_sync.py).

These compatibility paths let us change storage incrementally. They also meant that calling the scheme
Storage V2 did not imply every file had already moved or every old reference had disappeared.

## The album arrives again

The playlist now survived a move because it still referred to the same track row. Importing the album
again was different. A new random UUID would give it a new address, even if the release was already
in the catalogue. Storage V2 could preserve an existing identity; it could not discover that identity
from another copy of the music.

Later in April we introduced `entity_uid`, with UUIDv5 generation from a namespace and an identity key.
UUIDv5 makes the result repeatable for the same namespace and input. It does not decide whether that
input describes the same music. Crate still had to choose the keys and decide when to reuse an existing
row. [RFC 9562, UUIDv5](https://www.rfc-editor.org/rfc/rfc9562.html#section-5.5).

For albums, the generator preferred a MusicBrainz release-group ID, then a release ID. Without those,
it built a fallback from the artist identity, album names and year. Artist and track generators had
their own namespaces and fallback rules.

```python source="app/crate/entity_ids.py#L51-L57" commit="784df5d10f786aa012eb3a91fd1766810b174bdb"
    releasegroup_id = _normalize_identifier(musicbrainz_releasegroupid)
    if releasegroup_id:
        return _uuid5(_ALBUM_NAMESPACE, f"mb-releasegroup:{releasegroup_id}")

    album_id = _normalize_identifier(musicbrainz_albumid)
    if album_id:
        return _uuid5(_ALBUM_NAMESPACE, f"mb-album:{album_id}")
```

The release-group preference grouped an album at a broader level than a particular edition. The
fallback could change when its metadata changed, and text normalisation could collapse distinct
spellings. A repeatable UUID therefore still needed careful matching and preservation of existing
identities.

The identity tests made some of those choices explicit: normalised artist names generated the same
fallback UID, a release-group ID took precedence over album spelling, and identical normalised track
inputs produced the same UID. Those are matching rules we chose. Whether two editions,
live recordings or duplicate files should share an identity still depends on the inputs and the
catalogue's matching policy.
[Identity tests](https://github.com/thecrateapp/crate/blob/784df5d10f786aa012eb3a91fd1766810b174bdb/app/tests/test_entity_ids.py#L10-L59).

The album upsert kept an existing `entity_uid` when it found the row. New external identifiers became
lookup keys associated with it. We did not want discovering a MusicBrainz ID to replace every reference
to an album that was already known. [Identity preservation](https://github.com/thecrateapp/crate/blob/784df5d10f786aa012eb3a91fd1766810b174bdb/app/crate/db/repositories/library_album_upserts.py#L46-L108).

New path construction switched to `entity_uid`; the original `storage_id` became an optional legacy
alias. Playlist reads kept compatibility with both generations, preferring a numeric track ID and
then an entity UID before falling back to the old storage ID and paths:

```python source="app/crate/db/repositories/playlists_detail_reads.py#L40-L56" commit="784df5d10f786aa012eb3a91fd1766810b174bdb" "track_entity_uid"
                LEFT JOIN LATERAL (
                    SELECT id, entity_uid::text, path, title, filename, artist, album, album_id, duration
                    FROM library_tracks lt
                    WHERE lt.id = pt.track_id
                       OR (pt.track_entity_uid IS NOT NULL AND lt.entity_uid = pt.track_entity_uid)
                       OR (pt.track_storage_id IS NOT NULL AND lt.storage_id = pt.track_storage_id)
                       OR lt.path = pt.track_path
                       OR lt.path LIKE ('%/' || pt.track_path)
                    ORDER BY CASE
                        WHEN lt.id = pt.track_id THEN 0
                        WHEN pt.track_entity_uid IS NOT NULL AND lt.entity_uid = pt.track_entity_uid THEN 1
                        WHEN pt.track_storage_id IS NOT NULL AND lt.storage_id = pt.track_storage_id THEN 2
                        WHEN lt.path = pt.track_path THEN 3
                        ELSE 4
                    END
                    LIMIT 1
                ) lt ON TRUE
```

This was still a transition. The query deliberately carried several ways to resolve an old entry,
and matching by a path suffix remained weaker than having a direct identity. The new identity layer
made it possible to migrate those references without requiring every client and every saved playlist
to change at once.
[Legacy storage aliases](https://github.com/thecrateapp/crate/blob/784df5d10f786aa012eb3a91fd1766810b174bdb/app/crate/db/migrations/versions/019_make_storage_ids_legacy_optional.py#L18-L35).

The album's display name, catalogue references and file address could now change independently.
A corrected title left the managed path alone. A moved file kept its track row. When an import
matched an existing album, its new provider identifiers could attach to the identity already in use.
Old playlists still had their path fallbacks while those references caught up.

The directory tree is less readable now, and keeping the database matters more. The track's tags
still describe the music, but they do not replace its catalogue relationships. Filesystem changes
still need reconciliation with those rows. While a worker repairs a location, the playlist can keep
pointing at the track instead of retaining a folder name that has already changed.
