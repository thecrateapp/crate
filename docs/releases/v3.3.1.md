# Crate 3.3.1

Crate 3.3.1 fixes federation pairing, Listen permissions and a timeout in Admin's
Global Catalog status panel. It makes a peer's first catalogue sync much faster, and
fixes a race in which a stale sync could delete the catalogue a newer sync had just
written. The database goes from migration 158 to 160.

## Federation pairing

- **Approval.** Admin uses the pairing request ID instead of the peer's node ID.
  It distinguishes incoming requests from offers awaiting approval at the other
  instance, and shows when a new request is needed after expiry.
- **Retry interrupted approval.** A valid, already signed acceptance can be retried
  after a failed callback. The same signed message is reused; its deadline is not
  extended. Cloudflare browser challenges produce a useful error in Admin.
- **Preserve owner decisions.** Trust, grants and pairing completion are committed
  together after signature verification. Retrying a completed exchange does not
  overwrite later permission changes. A pending exchange cannot restore a grant
  changed after consent.
- **Accurate expiry.** Pairing deadlines respect the validity of the signed node
  descriptors and parent messages, including older incoming offers.

## Listen permissions

- **Standard Listen grants work.** The permission validator now accepts
  `data_saver`, which Listen and Trusted Library already include in their delivery
  profiles. Earlier builds could reject the entire grant with
  `invalid_constraints`, blocking catalogue access and playback.
- **Access limits remain.** Unknown delivery profiles are rejected, and the Listen
  preset continues to exclude original audio.

## Catalogue sync

- **Faster first sync.** A peer's manifest is imported a page at a time: each page of
  up to 500 records, its projection work and its resume point are saved in one
  transaction, instead of one transaction per record. Manifest pages are no longer
  capped by the search result limit, which made a large catalogue take thousands of
  requests.
- **Projection in the background.** Merging remote records into the Global Catalog no
  longer holds up the sync. It runs in bounded batches, artists before albums before
  tracks, and keeps going between batches without waiting for the scheduler.
- **Changes in commit order.** An instance publishes its catalogue changes in the order
  they were committed, so a peer following them sees every change, including an edit
  that returns to an earlier value or a delete after a restore. Manifest pages respect
  the grant's scope, and a bootstrap restarts cleanly when the sharing policy changes
  half-way.
- **Stale syncs are fenced.** Each sync of a peer's catalogue takes a new generation
  when it starts, and every page, deletion and checkpoint it writes checks that
  generation first. A sync that a newer one, a disable or a revocation has superseded
  stops without writing, instead of marking the newer sync's records as deleted or
  moving its checkpoint back. Within one sync the checkpoint only moves forward.
- **Duplicate requests.** Admin's sync buttons no longer queue a second sync of the
  same peer, or of all peers, while one is pending or running.

## Global Catalog

- **Status panel.** Active genre-assertion counters filter out invalidated history
  before aggregation, allowing PostgreSQL to use the existing partial index. This
  prevents a full historical scan from timing out the Admin status request while
  preserving exact counts.

## Upgrading

- Upgrade both federation peers to receive the permission-validation fix on both
  sides. Mutual Listen requires each owner to grant Listen independently; an empty
  library on one peer is valid.
- If a grant was temporarily restricted to `delivery=["balanced"]` to work around
  the older validator, reapply the standard Listen preset after upgrading that
  instance to restore Data Saver delivery.
- A pairing request that has expired still requires a new offer. A valid request
  interrupted by a transport failure can be retried without changing keys.
- **Migrations 159 and 160** run on start. 159 adds the outbox that orders catalogue
  changes; 160 adds the sync generation and its guards. Both are additive.
- **Rollback.** Do not start older images against a database at 159 or 160 without
  first running the explicit downgrade to 158: older publishers cannot drain the new
  outbox, and once a fenced sync has run, older receivers cannot write that peer's
  catalogue. See *Federation upgrade and rollback* in the technical docs.
- **From 3.2.x.** Upgrading from 3.2.x also brings everything in 3.3.0 live, including
  migrations 145 to 158 and Smart Mix stem separation. Set up the stems directory
  (`STEMS_DIR`, `CRATE_STEMS_THREADS`) as the 3.3.0 notes describe before you upgrade.
